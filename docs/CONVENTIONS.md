# 개발 규칙

ABSolid 코드를 고칠 때 지키는 약속을 한곳에 모았습니다. 프로젝트의 방향은 [계획](PLAN.md), 자세한 작업 순서는 [인수인계 안내](HANDOVER.md)에 있습니다.

## 1. 글쓰기

화면 문구, 주석, 문서, 커밋 메시지 모두 같은 규칙을 따릅니다.

- 화살표 기호를 쓰지 않습니다. 순서는 문장이나 번호 목록으로, 메뉴 경로는 "설정의 기타 메뉴"처럼 씁니다.
- 가운뎃점은 되도록 쓰지 않습니다. 나열은 쉼표나 "와", "또는"으로 씁니다. 화면의 짧은 데이터 줄 구분자로 쓸 때만 양옆을 한 칸씩 띄웁니다.
- 사용자에게 보이는 문구는 해요체로 씁니다. 무엇이 일어났고 다음에 무엇을 하면 되는지 한두 문장으로 씁니다.
- 오류 문구는 한국어로, 사용자가 할 수 있는 일을 알려 줍니다. 서버의 영어 오류를 그대로 보여 주지 않습니다.
- 주석은 한국어로, 코드가 "왜" 그렇게 됐는지를 적습니다.

**화면 문구와 언어 (한국어, 영어)**

- 화면에 보이는 문구는 모두 `t('한국어 원문')` 을 거칩니다 (`src/lib/i18n.js`). 버튼 글자, 안내, 오류, 확인 창, `aria-label`, `placeholder`, `alt` 모두 해당합니다.
- 새 문구를 넣으면 `src/lib/i18n.en.js` 에 영어를 함께 적습니다. 빠뜨리면 `src/lib/i18n.test.js` 가 어느 파일 몇째 줄인지 알려 주며 실패합니다.
- 값이 들어가는 문구는 글자를 이어 붙이지 않고 `t('멤버 {count}명', { count })` 처럼 씁니다. 언어마다 낱말 순서가 다르기 때문입니다. 숫자만 강조하는 문장은 `tSplit` 을 씁니다.
- 영어에서 단수와 복수가 갈리면 번역표에 함수로 적습니다 (예: 1 day, 2 days).
- 서버가 보내는 문구는 `tServer()` 가 바꿉니다. DB 함수에 새 오류 문구를 넣으면 번역표의 서버 문구 부분에도 영어를 적습니다.
- 개인정보 처리방침과 이용약관은 `src/components/legal/ko.jsx`(원본)와 `en.jsx`(번역) 두 파일을 함께 고칩니다.

## 2. 코드 스타일

- 포맷은 Prettier 가 맞춥니다. 세미콜론 없음, 작은따옴표, 한 줄 120자. 커밋 전에 `npm run format` 을 돌립니다.
- 문법 검사는 ESLint 가 합니다. `src/` 는 브라우저와 React 규칙, `server/` 와 `api/` 는 Node 규칙을 씁니다.
- 언어는 JavaScript 입니다. 화면은 `.jsx`, 나머지는 `.js` 입니다.
- 파일 이름은 화면과 부품이 `PascalCase.jsx`(`Home.jsx`, `BottomNav.jsx`), 그 밖의 코드는 `camelCase.js`(`storagePaths.js`) 입니다.
- 테스트는 대상 파일 옆에 `이름.test.js` 로 둡니다.

## 3. 폴더

| 폴더 | 무엇을 두나 |
| --- | --- |
| `src/pages/` | 화면 하나에 파일 하나. 화면 전용 부품은 하위 폴더(`pages/settings/`, `pages/group/`) |
| `src/components/` | 여러 화면이 함께 쓰는 부품. 기본 부품은 `ui.jsx` 에 모음 |
| `src/lib/` | 화면과 상관없는 계산과 규칙 (통계, 저장, 테마, 입력 검사) |
| `src/server/` | 앱에서 Supabase 와 서버를 부르는 함수 |
| `server/` | 자체 API 서버 (Hono) |
| `api/` | Vercel 서버 함수 입구. `server/app.js` 를 연결만 함 |
| `supabase/` | SQL, Edge Function, DB 보안 테스트 |
| `scripts/` | 아이콘, 스플래시 이미지, 소개 페이지의 휴대폰 틀 이미지 생성 스크립트 |

새 화면을 만들면 `src/lazyPages.js` 와 `src/App.jsx` 의 화면 전환 부분에도 추가합니다. 주소는 앱(`/`)과 소개 페이지(`/about`) 둘뿐이라 라우터를 쓰지 않고 `src/main.jsx` 가 나눕니다.

## 4. 화면 디자인

- 휴대폰 화면이 기준입니다. 내용 폭은 최대 480px(`max-w-120`) 입니다.
- 폭이 320px 인 폰에서도 확인합니다. 아이폰의 확대 화면 설정을 켜면 이 폭이 됩니다.
- 앱 화면에는 데스크톱 전용 배치가 없습니다. PC 에서도 같은 한 줄 화면이 가운데에 보이므로 `md:` 같은 화면 폭 분기는 쓰지 않습니다.
- 예외는 소개 페이지(`/about`)입니다. PC 에서도 보는 공개 페이지라 화면 전체 폭을 쓰고 `md:`, `lg:` 분기를 씁니다. 폭 320px 부터 1280px 까지 확인합니다.
- 소개 페이지의 휴대폰 속 화면은 캡처 사진 대신 앱의 실제 부품으로 그립니다. 앱 화면이 바뀔 때 사진을 다시 찍지 않아도 되게 하기 위해서입니다.
- 화면 아래에 붙는 요소(메뉴 바, 알림, 아래 여백)는 아이폰 홈 바 영역 `env(safe-area-inset-bottom)` 을 더합니다.
- 색은 `src/index.css` 의 이름 붙은 색(`bg-surface`, `text-dim`, `bg-brand` 등)만 씁니다. 색 값을 코드에 직접 쓰지 않습니다. 라이트와 다크가 이 색으로 함께 바뀝니다.
- 브랜드 빨강(`brand`)은 주요 버튼과 달성 표시에만 씁니다. 오류와 위험한 동작은 `danger` 색을 씁니다.
- 간격과 크기는 Tailwind 기본 단계(`mt-3`, `size-8`)를 씁니다. 대괄호 임의값(`pb-[...]`)은 홈 바 영역 계산처럼 기본 단계로 표현할 수 없을 때만 씁니다. 실험하느라 넣은 임의값은 값이 정해지면 기본 단계로 바꿉니다.
- 그라데이션과 흐림으로 만든 빛 효과는 쓰지 않습니다. 단색과 얇은 테두리로 구분합니다.
- 버튼, 카드, 입력칸 같은 기본 부품은 `src/components/ui.jsx` 의 것(`Card`, `Button`, `Sub`, `Modal` 등)을 씁니다. 클래스 합치기는 `cx` 를 씁니다.
- 움직임은 `motion-safe:` 를 붙여, 움직임 줄이기 설정을 켠 사람에게는 보이지 않게 합니다.
- 이모지는 쓰지 않습니다. 아이콘은 SVG 로 그립니다.
- 아이콘은 모두 선으로 그린 단순한 아이콘입니다. 채우기, 색 점, 강조색 면을 넣지 않고 `currentColor` 선만 씁니다.

## 5. 서버와 데이터

**앱에서 부르는 함수 (`src/server/api.js`)**

- 조회 함수는 비회원이면 빈 값을 돌려줍니다.
- 사용자가 누른 동작이 실패하면 한국어 문구를 담은 `Error` 를 던집니다.
- 함수를 추가하면 [API 명세](API.md)의 목록에도 적습니다.

**DB (`supabase/`)**

- 검증이 필요한 쓰기는 테이블에 직접 쓰지 않고 서버 함수(SQL)로 만듭니다.
- 새 SQL 은 `supabase/vX.Y-이름.sql` 로 만들고, 같은 내용의 권한 테스트를 `supabase/tests/` 에 추가합니다.
- 권한은 RLS 로 막습니다. 앱 코드의 확인은 보조일 뿐입니다.

**자체 API 서버 (`server/`)**

- 로그인이 필요한 주소는 `requireUser` 미들웨어를 앞에 세웁니다.
- 토큰이 없거나 틀리면 401, Supabase 에 연결하지 못하면 503 을 돌려줍니다. 오류 응답은 `{ error }` 형식입니다.
- DB 는 요청한 사용자의 토큰으로 접근해 RLS 가 그대로 적용되게 합니다. 서비스 키는 꼭 필요한 기능에만 씁니다.
- 응답에는 필요한 값만 골라 담습니다. 사용자 정보를 통째로 내보내지 않습니다.
- 새 주소는 `server/app.test.js` 에 테스트를 추가하고 [API 명세](API.md) 5절에 적습니다.
- 앱 코드는 실제로 있는 서버 주소만 부릅니다. 아직 없는 주소를 있다고 가정하고 화면 코드를 먼저 쓰지 않습니다. `server/app.js` 에서 주소를 확인한 뒤 연결합니다.

**비밀 값**

- 서비스 키, VAPID 비밀 키 같은 비밀 값은 저장소에 넣지 않습니다. Vercel 과 Supabase 환경 변수에만 둡니다.
- `.env` 에는 공개해도 되는 값(`VITE_` 로 시작하는 주소와 공개 키)만 둡니다. `.env` 파일 자체도 커밋하지 않습니다(`.gitignore` 에 등록됨).
- 비밀 값을 실수로 커밋했으면 지우는 것으로 끝내지 않고 그 키를 새로 발급받아 교체합니다.

## 6. 브랜치와 커밋

두 명이 함께 개발합니다. 담당은 [계획](PLAN.md) 2절에 있습니다.

**브랜치**

- `main` 은 배포되는 코드입니다. main 에 들어가면 Vercel 이 바로 배포합니다.
- main 에 직접 커밋하지 않습니다. 모든 변경은 작업 브랜치에서 하고 PR 로 합칩니다. 버전 올리기도 PR 로 합니다 (7절). GitHub 의 브랜치 보호 규칙이 main 직접 push 를 막습니다.
- 작업 브랜치 이름은 종류를 앞에 붙입니다. 새 기능은 `feat/이름`, 버그 수정은 `fix/이름`, 설정과 도구는 `chore/이름` 입니다. 예: `feat/backend`, `feat/3d-videos`
- 오래 가는 작업 브랜치는 자주 `git merge main` 으로 main 을 받아 옵니다. 오래 벌어질수록 충돌이 커집니다.

**작업 순서**

1. `git switch main` 과 `git pull` 로 최신 코드를 받습니다.
2. 작업 브랜치를 만듭니다. 이미 있는 브랜치면 `git merge main` 으로 최신 main 을 받습니다.
3. 구현하고 아래 "커밋 전 확인"을 합니다.
4. 커밋하고 push 합니다.
5. GitHub 에서 PR 을 엽니다. 무엇을 왜 바꿨는지, 어떻게 확인했는지 적습니다. 화면이 바뀌었으면 캡처를 붙입니다.
6. Vercel 이 PR 에 달아 주는 미리보기 주소에서 확인합니다.
7. CI 가 통과하고 미리보기에서 확인했으면 합칩니다. 상대의 승인은 필수가 아닙니다. 합친 브랜치는 지웁니다.

**PR 과 확인**

- PR 하나에는 한 가지 일만 담습니다. 작을수록 빨리 확인됩니다.
- 합치기 전에 올린 사람이 직접 확인합니다: CI(문법 검사, 테스트, 빌드, DB 테스트)가 통과했는지, 미리보기에서 동작하는지, 이 문서의 규칙을 지켰는지.
- 상대의 승인은 필수가 아닙니다. 상대의 의견이 필요한 변경(함께 쓰는 화면 코드, 구조 변경, 상대 담당 폴더)은 PR 에서 확인을 부탁하고 답을 받은 뒤 합칩니다.
- 합칠 때는 GitHub 의 "Create a merge commit" 을 씁니다. "Squash" 로 합치면 커밋이 새로 만들어져 버전 태그가 main 밖의 커밋을 가리키게 됩니다.
- 충돌은 main 이 아니라 작업 브랜치에서 풉니다. 작업 브랜치에서 `git merge main` 으로 풀고 push 하면 PR 에 반영됩니다.
- 상대가 맡은 폴더를 고쳐야 하면 먼저 말합니다. 담당 폴더는 아래 표와 같습니다.

| 담당 | 주로 고치는 곳 |
| --- | --- |
| 백엔드 | `server/`, `api/`, `supabase/`, `src/server/`, `docs/API.md` |
| 3D 운동 영상 | `prototypes/situp-render/`, 영상을 앱에 연결할 때의 `src/pages/Workout.jsx` 와 설정의 모델 선택 |
| 함께 | 그 밖의 화면 코드(`src/`), `docs/CHANGELOG.md`, `docs/SPRINT_BACKLOG.md`, 그 밖의 문서 |

- 변경 기록은 두 사람이 같은 "다음 버전" 자리를 고쳐 충돌이 나기 쉽습니다. 충돌이 나면 양쪽 줄을 모두 남깁니다.

**커밋 메시지**

`종류: 무엇을 했는지` 형식으로, 한국어로 짧게 씁니다.

| 종류 | 언제 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `style` | 간격, 색, 문구처럼 보이는 것만 다듬기 |
| `design` | 화면 구성을 바꾸는 디자인 변경 |
| `refactor` | 동작은 그대로 두고 코드 구조 정리 |
| `perf` | 속도 개선 |
| `docs` | 문서만 수정 |
| `chore` | 설정, 도구, 의존성 |

예: `fix: 좁은 폰에서 최근 7일 동그라미가 붙던 문제`

**커밋 전 확인**

1. `npm run check` 가 통과하는지 봅니다. 문법 검사, 포맷 검사, 테스트, 빌드를 한 번에 합니다.
2. DB 를 고쳤으면 `npm run test:db` 도 돌립니다.
3. 화면이 바뀌었으면 실제 브라우저에서 폭 320px 와 375px 두 가지로 눌러 봅니다. 화면 자동 테스트가 없기 때문입니다.
4. [변경 기록](CHANGELOG.md)의 "다음 버전"에 **추가**, **변경**, **수정**, **내부**, **서버**로 나눠 적고 같은 커밋에 넣습니다. 서버 함수나 API 가 바뀌면 [API 명세](API.md)도 고칩니다.

## 7. 버전과 배포

- 버전은 main 에 내보낼 때만 올립니다. 작업 브랜치에서는 올리지 않습니다.
- 버전 올리기는 저장소 주인(백엔드 담당)이 합니다. 두 사람이 따로 올리면 같은 번호의 태그가 겹칩니다.
- 버전 올리기도 PR 로 합니다. 최신 main 에서 `chore/release-버전` 브랜치를 만들어 아래 순서로 하고, PR 을 열어 합칩니다.
- 올리는 크기는 변경에 맞춥니다.
  - `patch`: 버그 수정, 작은 다듬기 (0.6.2 에서 0.6.3)
  - `minor`: 새 기능, 큰 구조 변경 (0.6.3 에서 0.7.0)
  - `major`: 정식 출시
- 버전을 올리기 전에 변경 기록의 "다음 버전" 제목을 새 버전 번호와 날짜로 바꿉니다.

```bash
git switch main
git pull
git switch -c chore/release-0.8.0
# docs/CHANGELOG.md 의 "다음 버전" 제목을 "0.8.0 (날짜)" 로 바꾼 뒤
git add docs/CHANGELOG.md
git commit -m "docs: 0.8.0 변경 기록"
npm version minor
git push -u origin chore/release-0.8.0 --follow-tags
```

push 한 뒤 GitHub 에서 PR 을 열고 "Create a merge commit" 으로 합칩니다. 합쳐지면 Vercel 이 새 버전을 배포합니다.

`npm version` 은 버전만 올리는 커밋과 태그(`v0.8.0`)를 따로 만듭니다. 설정 화면 아래의 버전 표시가 이 값입니다. 태그는 브랜치의 버전 커밋에 붙고, PR 을 합치면 그 커밋이 main 에 들어옵니다.

**main 보호 규칙** (GitHub 저장소의 Settings, Rules, Rulesets)

| 규칙 | 설정 |
| --- | --- |
| Require a pull request before merging | 켬. 필요한 승인 수는 0 |
| Require status checks to pass | 켬. CI 검사 |
| Block force pushes | 켬 |
| Restrict deletions | 켬 |
| Bypass list | 비움 (저장소 주인도 PR 로 합침) |

## 8. 하지 말 것

위 규칙 중 어기면 문제가 큰 것만 다시 모았습니다.

- 비밀 값(서비스 키, VAPID 비밀 키, 크론 비밀 값)을 화면 코드나 커밋에 넣지 않습니다.
- `.env` 를 커밋하지 않습니다.
- 검증이 필요한 쓰기를 앱에서 테이블에 직접 하지 않습니다. 서버 함수를 거칩니다.
- 서버 응답에 사용자 정보를 통째로 담지 않습니다.
- 아직 없는 서버 주소를 가정한 화면 코드를 쓰지 않습니다.
- 색 값을 코드에 직접 쓰지 않고, 브랜드 빨강을 오류 표시에 쓰지 않습니다.
- 그라데이션, 이모지, 화살표 기호를 쓰지 않습니다.
- main 에 직접 커밋하거나 push 하지 않습니다. 버전 올리기와 충돌 풀기도 브랜치와 PR 로 합니다.
- CI 가 실패한 PR 을 합치지 않습니다.
- PR 을 Squash 로 합치지 않습니다 (버전 태그가 main 밖을 가리키게 됨).
- 상대가 맡은 폴더를 말없이 고치지 않습니다.
- 작업 브랜치에서 버전을 올리지 않습니다.
- `npm run check` 가 실패한 채로 main 에 합치지 않습니다.

**설정 파일**

- `.claude/settings.json`: 함께 쓰는 훅 (3번부터 11번). 저장소에 올라가서 두 사람 모두에게 적용됩니다.
- `.claude/settings.local.json`: 내 컴퓨터에만 적용하는 훅 (1번, 2번). 저장소에 올리지 않습니다. 필요하면 각자 같은 내용으로 만듭니다.
- `CLAUDE.local.md`: 개인 작업 방식. 저장소에 올리지 않습니다.
- `.claude/` 의 나머지(스킬, 미리보기 설정)도 저장소에 올리지 않습니다 (`.gitignore`).

**동작 방식**

- 새로 쓴 내용만 검사합니다. 예전부터 있던 내용은 고칠 때 함께 정리합니다.
- 명령 검사는 파일에 쓰는 글(heredoc 본문)은 빼고 명령 부분만 봅니다.
- 작업을 끝낼 때 검사는 한 번만 막습니다. 알림이 이번 변경에 해당하지 않으면 이유를 말하고 끝낼 수 있고, 지난번과 바뀐 게 없으면 다시 알리지 않습니다.
- 훅 자체에 오류가 나면 작업을 막지 않고 넘어갑니다.
- 규칙을 바꾸면 `hooks.mjs` 와 `hooks.test.js`, 이 표를 함께 고칩니다. 설정을 바꾼 뒤에는 Claude Code 세션을 새로 열어야 확실히 적용됩니다.
