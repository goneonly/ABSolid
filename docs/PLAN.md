# PLAN.md — ABSolid

> 프로젝트의 방향을 정하는 문서입니다. 새로 맡는 개발자와 그 개발자의 Claude 가 가장 먼저 읽습니다.
> 이 문서는 **무엇을, 왜, 어떤 순서로** 만드는지를 다룹니다. 어떻게 쓰는지는 [개발 규칙](CONVENTIONS.md), 지금 코드가 어떻게 돌아가는지는 [인수인계 안내](HANDOVER.md), 할 일의 진행 상태는 [스프린트 백로그](SPRINT_BACKLOG.md)에 있습니다.

- **프로젝트명**: ABSolid (ABS + Solid). 저장소 이름도 `ABSolid`
- **운영 주소**: https://absolid.vercel.app
- **문서 상태**: v0.3, 2026-11-15. 3D 자체 모델 방향 추가. 앱 버전 0.7.0 기준

---

## 1. 한 줄 정의와 핵심 원칙

**친구들과 그룹을 만들어 매일 10분 복근 운동을 하고, 기록을 나누며 꾸준함을 만드는 모바일 웹앱.**

앱의 문구는 "10분의 꾸준함이 만드는 단단함"입니다. 모든 기능 결정은 아래 다섯 원칙에 맞아야 합니다.

1. **꾸준함이 먼저** — 운동을 잘하게 만드는 앱이 아니라 매일 하게 만드는 앱입니다. 하루 한 번, 영상 하나, 짧게 끝납니다. 연속 운동일(streak)이 가장 중요한 숫자입니다.
2. **함께 한다** — 혼자 쓰는 기록 앱이 아닙니다. 그룹, 리더보드, 인증샷, 응원이 계속하게 만드는 힘입니다.
3. **웹앱이 본질** — 코드는 웹 하나입니다. 스토어에 올릴 때도 웹앱을 감싸서 올리고, 따로 네이티브 앱을 다시 만들지 않습니다.
4. **보안은 서버가 책임** — 화면에서 버튼을 숨기는 것은 편의일 뿐입니다. 권한은 DB 정책(RLS)과 서버 함수에서 확인하고, 운동 완료 같은 기록은 서버가 검증합니다.
5. **직접 소유** — 서버 로직과 운동 영상처럼 서비스의 중심이 되는 것은 남의 것에 기대지 않고 직접 갖는 방향으로 갑니다.

> "운동 종류를 늘리는 것"보다 "매일 돌아오게 하는 것"이 먼저입니다. 새 기능이 이 축을 흐리면 넣지 않습니다.

## 2. 누가 쓰나

- **사용자**: 친구, 동기, 동아리처럼 이미 아는 사람들끼리 함께 운동 습관을 만들고 싶은 사람. 헬스장에 갈 시간은 없지만 집에서 10분은 낼 수 있는 사람.
- **쓰는 장면**: 휴대폰 홈 화면의 아이콘을 눌러 열고, 오늘 영상을 끝까지 따라 하고, 인증샷을 올리고, 그룹 친구에게 응원을 보냅니다.
- **비회원**: 로그인 없이도 쓸 수 있습니다. 기록은 그 기기에만 남습니다. 가입하면 그룹과 응원을 쓸 수 있습니다.
- **만드는 사람**: 두 명이 함께 개발합니다 (2026-11-15 부터).

| 담당 | 맡는 일 | 주로 고치는 곳 |
| --- | --- | --- |
| 백엔드 담당 (저장소 주인) | 자체 백엔드(단계 1), 배포와 버전 올리기, Supabase 와 Vercel 관리 | `server/`, `api/`, `supabase/`, `src/server/` |
| 3D 영상 담당 | 자체 3D 운동 영상(단계 4), 영상을 앱에 연결 | `prototypes/situp-render/`, `src/pages/Workout.jsx` |

두 일은 고치는 폴더가 거의 겹치지 않아 나란히 진행합니다. 화면 코드와 문서는 함께 고칩니다. 협업 방법은 [개발 규칙](CONVENTIONS.md) 6절에 있습니다.

## 3. 기술 스택 (확정)

| 레이어 | 선택 | 비고 |
| --- | --- | --- |
| 화면 | **React 18 + Vite 8 + JavaScript + Tailwind CSS 4** | 색과 크기는 §6 디자인 토큰 |
| 형태 | **PWA** (홈 화면 추가, 푸시 알림, 서비스 워커) | 최종 배포처는 플레이스토어 (TWA) |
| 인증, DB, 저장소 | **Supabase** (Auth, Postgres + RLS, Storage, Edge Functions) | 계속 사용 |
| 자체 API 서버 | **Hono** (JavaScript, Vercel 서버 함수) | 기능을 하나씩 옮기는 중 |
| 테스트 | Vitest (단위), SQL 테스트 (DB 권한) | 화면 자동 테스트는 아직 없음 |
| 배포 | Vercel (main 에 push 하면 자동 배포) | Node.js 24 |
| 그 밖 | Cloudflare Turnstile (캡차), Vercel Analytics, YouTube (운동 영상) | 영상은 자체 3D 영상으로 바꿀 예정 |

**정해 둔 방향**

- 언어는 JavaScript 로 시작했고, 자체 API 서버의 흐름에 익숙해지면 TypeScript 로 옮깁니다.
- 자체 API 서버는 Supabase 를 대체하지 않습니다. 로그인, DB, 사진 저장은 Supabase 에 두고 그 앞에 서버를 세웁니다.
- 항상 켜진 서버가 필요해지면 Vercel 서버 함수에서 Railway 나 Fly.io 로 옮깁니다.

> 비밀 키(Supabase 서비스 키, 푸시 개인 키, 크론 비밀 값)는 서버 환경 변수에만 둡니다. 화면 코드와 저장소에는 넣지 않습니다.

## 4. 시스템 구조

**지금 (옮기는 중)**

```
[React PWA]
   ├─ 대부분의 기능: Supabase 를 직접 호출 (RLS 와 서버 함수가 검증)
   └─ 옮긴 기능:     /api 로 요청
                       │
                 [자체 API 서버 (Hono)]
                       │  요청한 사용자의 토큰으로 접근
                 [Supabase: Auth, Postgres(RLS), Storage, Edge Functions]
```

2026-11-15 기준으로 앱의 모든 기능은 아직 Supabase 를 직접 부릅니다. 자체 API 서버에는 상태 확인(`/api/health`)과 내 정보(`/api/me`) 주소만 있고, 앱은 아직 이 주소를 쓰지 않습니다. 처음 옮길 기능은 공지 조회입니다.

**목표**

```
[React PWA]
   │  /api 요청 (로그인 토큰)
[자체 API 서버]   토큰 확인, 검증, 집계
   │
[Supabase]        로그인, DB, 사진 저장
```

**자체 API 서버의 요청 처리 순서**

1. 앱이 `Authorization: Bearer <로그인 토큰>` 과 함께 `/api/...` 로 요청합니다.
2. 미들웨어(`requireUser`)가 토큰을 Supabase 에 확인합니다. 없거나 틀리면 401, Supabase 에 연결하지 못하면 503 입니다.
3. 서버가 그 사용자의 토큰으로 DB 를 읽고 씁니다. RLS 가 그대로 적용됩니다.
4. 필요한 값만 골라 JSON 으로 돌려줍니다.

**옮기는 원칙**

- 기능을 하나씩 옮깁니다. 옮기는 동안에도 앱은 멈추지 않습니다.
- 화면 코드는 바뀌지 않습니다. 바뀌는 곳은 `src/server/api.js` 뿐입니다.
- 옮긴 기능은 Supabase 직접 접근을 닫습니다. 같은 기능이 두 길로 열려 있는 기간을 짧게 합니다.

## 5. 화면

공통 구성: **위쪽 로고** + **본문** + **아래 메뉴 바**(그룹, 가운데 시작 또는 홈 버튼, 설정). 화면 폭은 최대 480px 이고 PC 에서도 같은 화면이 가운데에 보입니다.

| 화면 | 구성 | 중요도 |
| --- | --- | --- |
| **홈** | 연속 운동일, 오늘 운동 상태, 주간 리포트(이번 주 인증, 달성률, 최근 7일), 공지와 리마인더 배너 | 핵심 |
| **운동** | 오늘 날짜에 맞는 Day 1부터 30 영상 재생. 80% 이상 보면 완료. 완료 화면에서 인증샷 첨부 | 핵심 |
| **그룹** | 그룹 만들기와 초대 코드 참여, 멤버 현황, 리더보드, 오늘의 인증샷, 응원, 신고와 차단 | 핵심 |
| **로그인, 회원가입** | 이메일 가입과 인증, 캡차, 비회원으로 시작 | 기본 |
| **설정** | 프로필(닉네임, 사진), 알림, 화면 테마, 홈 화면 추가 안내, 기록 내보내기, 차단 목록, 탈퇴 | 기본 |
| **관리자** | 대시보드, 회원, 그룹, 신고, 공지 관리 | 운영 |

> 홈의 연속 운동일과 운동 화면이 이 앱의 중심입니다. 그룹은 다시 돌아오게 만드는 장치입니다.

## 6. 디자인 토큰 — 메인 컬러는 빨강

브랜드 색은 **빨강**입니다. 기본은 다크 테마이고 라이트 테마와 시스템 설정 따르기를 지원합니다. 값은 `src/index.css` 한 곳에 있습니다.

| --- | --- | --- | --- |
| `bg` | `#141519` | `#f5f6f8` | 앱 배경 |
| `surface` | `#1e2026` | `#ffffff` | 카드 |
| `surface-2` | `#26282f` | `#f0f1f4` | 카드 안의 칸, 비활성 원 |

| `dim` | `#9a9ea8` | `#626873` | 보조 글자 |
| `brand` | `#ff3b30` | `#d0261b` | 주요 버튼, 달성 표시 |

## 7. 데이터 모델 (Supabase Postgres)

모든 테이블에 RLS 가 걸려 있습니다. 자세한 권한과 서버 함수는 [API 명세](API.md)에 있습니다.

```
profiles(닉네임, 이름, 전화번호, 프로필 사진, role, 활성 여부, 동의 기록)

-- 운동
workouts(user_id, date, day, completed_at, photo_url)     -- 운동 기록
workout_sessions(...)                                     -- 시청 세션. 함수만 접근

-- 그룹
groups(name, invite_code, max_members, members_only, created_by, photo_url)
group_members(group_id, user_id)
cheers(from_user, to_user, date, kind)                    -- 응원. 하루 한 번
user_blocks(blocker, blocked)                             -- 차단
reports(...)                                              -- 인증샷 신고

-- 운영
announcements(...)                                        -- 공지
app_config(playlist_id)                                   -- 앱 설정
push_subscriptions(...)                                   -- 푸시 구독
blocked_email_domains, join_attempts                      -- 가입, 초대 코드 남용 방지
```

저장소(Storage) 버킷은 세 개입니다. `photos`(인증샷, 비공개), `avatars`(프로필 사진), `group-photos`(그룹 사진).

**지켜야 할 것**

- 운동 기록과 응원은 서버 검증 함수로만 만듭니다. 앱이 테이블에 직접 쓰지 않습니다.
- 비회원 기록은 서버에 가지 않고 기기의 localStorage 에만 있습니다. 키는 `src/lib/storage.js` 에서만 정의합니다.

## 8. 개발 단계

각 단계는 **완료 기준**을 채우면 다음으로 넘어갑니다. 지금 어디까지 했는지는 [스프린트 백로그](SPRINT_BACKLOG.md)에서 관리하고, 이 문서에는 순서와 이유만 둡니다.

### 단계 0 — 웹앱 (완료)

- 운동, 기록, 그룹, 응원, 알림, 신고와 차단, 관리자, 회원 탈퇴까지 갖춘 PWA.
- **완료 기준**: 운영 주소에서 가입부터 운동 완료, 그룹 참여까지 끊김 없이 동작. 달성.

### 단계 1 — 자체 백엔드 (진행 중, 우선순위 높음, 백엔드 담당)

- Supabase 앞에 API 서버를 세우고 기능을 하나씩 옮깁니다. 순서는 뼈대와 토큰 확인, 공지 조회, 운동 시작과 완료 검증, 그룹 현황과 리더보드 집계, 응원과 알림, 마지막으로 옮긴 기능의 직접 접근 닫기입니다.
- 왜 먼저인가: 서버 로직을 직접 갖는 것이 원칙 5이고, 이후의 집계와 검증 기능이 이 위에 올라갑니다.
- **완료 기준**: 옮긴 기능은 앱이 Supabase 를 직접 부르지 않고, 직접 부르면 거절됩니다. 단위 테스트와 DB 보안 테스트가 통과합니다.

### 단계 2 — 출시 전 권리 확인 (우선순위 높음)

- 푸앙이 캐릭터 이스터에그의 사용 규정, 운동 영상(외부 YouTube 재생목록)의 사용 조건을 확인합니다. 메일 발신 주소를 개인 계정에서 서비스 전용 계정으로 바꿉니다.
- 왜 스토어 등록 전인가: 공개 배포 뒤에는 되돌리기 어렵습니다.
- **완료 기준**: 권리가 불확실한 요소가 앱에 남아 있지 않습니다.

### 단계 3 — 플레이스토어 등록 (우선순위 높음)

- 웹앱을 TWA(Trusted Web Activity)로 감싸 올립니다. 화면 코드는 그대로 씁니다.
- **완료 기준**: 플레이스토어에서 내려받아 가입부터 운동 완료까지 동작합니다.

### 단계 4 — 자체 3D 운동 영상 (진행 중, 우선순위 중간, 3D 영상 담당)

- 단계 1과 나란히 진행합니다. 영상을 만드는 일은 앱 코드와 떨어져 있어 서로 기다릴 필요가 없습니다.

- 외부 YouTube 영상을 Blender 로 만든 3D 영상으로 바꿉니다. 설정에서 남녀 모델을 고릅니다.
- 모델은 외부 모델이 아니라 직접 만든 근육 해부도 스타일 모델입니다 (참고 앱 Fleek). 얼굴과 피부가 없는 무채색 몸에, 그 운동에 쓰는 근육만 브랜드 빨강으로 칠합니다.
- 순서: 자체 모델 만들기, 근육 부위 나누기, 다리 들기 하나로 품질 확인, 30일치 렌더, 앱에 연결.
- 왜 모델부터인가: 지금 시제품의 외부 모델은 재배포 권리가 불확실합니다. 모델이 바뀌면 영상을 모두 다시 렌더해야 하므로 영상을 늘리기 전에 정합니다.
- **완료 기준**: Day 1부터 30까지 모든 운동이 자체 영상으로 재생됩니다. 자세한 내용은 [인수인계 안내](HANDOVER.md)의 "feat: 3D 모델링"에 있습니다.

### 단계 5 — 헬스장 운동 루틴 (우선순위 중간)

- 운동 장소 선택의 "헬스장에서"가 준비 중으로 막혀 있습니다. 루틴을 만들어 엽니다.
- **완료 기준**: 집과 헬스장 중 골라 그날의 운동을 시작할 수 있습니다.

### 단계 5-1 — 근육 지도 (우선순위 낮음)

- 자체 모델로 앞뒤 근육 지도 이미지를 만들어, 이번 주에 쓴 근육을 홈이나 주간 리포트에 보여 줍니다.
- 왜 나중인가: 3D 영상(단계 4)의 모델과 근육 부위 나누기가 끝나야 만들 수 있습니다.
- **완료 기준**: 주간 리포트에서 이번 주에 운동한 근육이 그림으로 보입니다.

### 단계 6 — 다지기 (우선순위 낮음)

- 콘텐츠 보안 정책(CSP) 도입, 주요 흐름의 화면 자동 테스트(예: Playwright).
- **완료 기준**: 로그인, 운동 완료, 그룹 참여가 자동 테스트로 확인됩니다.

## 10. 환경 변수

```bash
# .env (로컬)과 Vercel 환경 변수 — 브라우저에 노출돼도 되는 공개 값만
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
VITE_VAPID_PUBLIC_KEY=        # 푸시 알림 공개 키. 없으면 알림 꺼짐
VITE_TURNSTILE_SITE_KEY=      # 캡차 사이트 키. 없으면 캡차 표시 안 함

# Supabase Edge Function 시크릿 — 저장소와 .env 에 넣지 않음
VAPID_PUBLIC_KEY=
VAPID_PRIVATE_KEY=
VAPID_SUBJECT=
CRON_SECRET=
```

- Supabase 키가 없으면 앱은 비회원 모드로만 동작합니다.
- 자체 API 서버도 `VITE_SUPABASE_URL` 과 `VITE_SUPABASE_ANON_KEY` 를 읽습니다. 서비스 키가 필요한 기능을 옮길 때는 Vercel 환경 변수에만 추가합니다.

## 11. 범위와 결정이 필요한 것

**지금 있는 것**: 인증, 운동과 서버 검증, 연속 운동일과 주간 리포트, 그룹과 리더보드, 인증샷, 응원, 푸시 알림, 신고와 차단, 관리자, 회원 탈퇴, 화면 테마.

**만들 것**: 자체 백엔드, 플레이스토어 등록, 자체 3D 운동 영상(자체 모델), 헬스장 루틴, 근육 지도, CSP, 화면 자동 테스트.

**하지 않는 것**

- 네이티브 앱을 따로 다시 만들기. 웹앱을 감쌉니다.
- iOS 앱스토어 등록. 먼저 플레이스토어입니다. 아이폰은 홈 화면 추가로 씁니다.
- Supabase 를 통째로 걷어 내기. 로그인, DB, 저장소는 계속 씁니다.
- 데스크톱 전용 화면.

**결정이 필요한 것**

1. **운동 영상** — 자체 3D 영상이 다 만들어지기 전에 스토어에 올린다면, 그동안 YouTube 재생목록을 계속 쓸 수 있는지 사용 조건 확인.
2. **3D 영상 저장 위치** — 앱에 포함할지(`public/`), 외부 저장소(Supabase Storage 등)에 둘지. 30일치 남녀 영상이면 용량이 큽니다.
3. **3D 자체 모델** — MPFB 로 직접 만들지, 외주를 맡길지. MPFB 결과물의 상업적 사용 조건 확인.
4. **푸앙이 이스터에그** — 사용 규정을 확인할지, 뺄지.
5. **메일 발송** — 전용 Gmail 계정으로 충분한지, 메일 서비스(Resend 등)로 옮길지.
6. **TypeScript 전환 시점** — 자체 백엔드의 어느 단계부터 옮길지.

## 12. 개발 규칙

전체 규칙은 [개발 규칙](CONVENTIONS.md)에 있습니다. 가장 중요한 것만 적습니다.

- 브랜치는 `feat/`, `fix/`, `chore/` 로 시작합니다. main 에 직접 커밋하지 않고, 작업 브랜치에서 PR 을 열어 상대가 확인한 뒤 합칩니다.
- 커밋 메시지는 `feat: 무엇을 했는지` 형식으로 한국어로 씁니다.
- 커밋 전에 `npm run check` 를 통과시키고, [변경 기록](CHANGELOG.md)의 "다음 버전"에 적습니다. 서버 함수나 API 가 바뀌면 [API 명세](API.md)도 고칩니다.
- 버전은 main 에 내보낼 때만, 저장소 주인이 올립니다.
- 글에는 화살표 기호와 이모지를 쓰지 않고, 가운뎃점은 되도록 쓰지 않습니다. 사용자에게 보이는 문구는 해요체입니다.
- 비밀 값은 저장소에 넣지 않습니다.

- 커밋, push, PR 같은 git 작업은 사람이 직접 합니다. Claude 는 명령을 제안만 합니다. (백엔드 담당의 방식이고, 3D 영상 담당은 자기 방식을 정할 수 있습니다.)

- 자체 백엔드는 배우면서 만듭니다. Claude 가 통째로 써 주지 않고, 개념을 설명하고 뼈대와 힌트를 준 뒤 핵심 코드는 백엔드 담당이 씁니다.
